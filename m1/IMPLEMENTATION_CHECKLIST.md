### B-1 fix (2026-10-31) — verified live
- **Probe evidence (scratch DB `cl_probe`):** (1) `SET row_security TO off` inside a SECURITY DEFINER function does NOT bypass RLS — it makes affected queries raise `query would be affected by row-level security policy` (hint: `ALTER TABLE ... NO FORCE ROW LEVEL SECURITY`). Session-level `SET row_security = off` behaves the same. (2) A SECURITY DEFINER function owned by a non-owner role cannot insert into a FORCE-RLS table with no applicable policy. (3) Working design verified: membership-based `merchants` SELECT via an `EXISTS` subquery over `merchant_memberships` (whose own SELECT policy lets a user's OWN rows through, so the subquery works with no bypass), plus `NO FORCE` on the two identity-root tables so the table-owner-owned creation function can insert without a tenant context. Probe: user A sees 1 merchant / 1 membership, user B sees 0/0, anonymous 0/0; direct INSERT by the runtime role denied. (An early probe round returned 0 rows for A only because each `psql -c` runs in its own transaction and transaction-local `set_config(..., true)` evaporated between commands — a probe artefact, not a design failure.)
- **Implemented (v0.1 §E.3):** `app/db/rls.sql` — new `app_current_user_id()` helper (CL-06-style, v0.1 E.2 name; deliberately asymmetric with `app.current_merchant_id`, recorded as discrepancy 2); `merchants` SELECT policy now membership-based (`EXISTS (SELECT 1 FROM merchant_memberships ... status = 'active')`); old `merchants_tenant_insert` policy DROPPED, intentionally not recreated (no general INSERT policy — direct merchant INSERT by the runtime role is denied by default-deny); `merchant_memberships` FOR ALL policy replaced by SELECT (`user_id = app_current_user_id() OR merchant_id = app_current_merchant_id()`), INSERT and UPDATE (merchant-context only), no DELETE policy; `ALTER TABLE ... NO FORCE ROW LEVEL SECURITY` on `merchants` and `merchant_memberships` only (all other tenant tables keep FORCE); index `ix_merchant_memberships_user_active (user_id, status, merchant_id)`; new controlled function `public.create_workspace(p_user_id, p_name, p_trading_name) RETURNS uuid` — SECURITY DEFINER, `SET search_path TO public, pg_catalog`, schema-qualified objects, no dynamic SQL, `REVOKE ALL ... FROM PUBLIC`, `GRANT EXECUTE ... TO courierledger_runtime`; validates user exists/active and name 1–200 chars, inserts merchant + owner membership atomically, returns the id. **Ownership note:** the function is owned by the role that applies `rls.sql` — `courierledger`, the table-owner / migration role in this environment. ### B-3 fix (2026-10-31) — verified live
- **New service** `backend/app/services/idempotency_service.py` (the only module that may UPDATE `idempotency_keys`): implements the CL-14/CL-19/CL-24 conditional-update predicates. Lease comparisons use the database clock at statement-execution time — PostgreSQL `clock_timestamp()`, NEVER `now()` (transaction-start time) — stated in the module docstring and in the SQL it builds (`func.clock_timestamp()`; compiled form verified: `clock_timestamp()`, `clock_timestamp() + make_interval(secs => 300)`, predicate `status = 'in_progress' AND claim_token = ... AND lease_expires_at > clock_timestamp()`). Uniform ownership rule (CL-24): completion, worker-reported failure and renewal all require status `in_progress` AND matching `claim_token` AND `lease_expires_at > clock_timestamp()`; zero rows means ownership lost — caller must roll back, do not complete. Two clocks never conflated (CL-14): `expires_at` is the 24h replay horizon; `lease_expires_at` is the ownership horizon (defaults: 5 min `import_create`, 10 min `run_create`). Functions never commit — the caller owns the transaction. `claim()` returns `("claimed", row)` or `("replay", row)` and raises `IdempotencyConflictError` on hash mismatch (CL-04), live owner, previously failed key, or attempt cap (5, CL-14; cap breach transitions the row to `failed`); concurrent first claims handled with a SAVEPOINT + UNIQUE-constraint retry. `complete()` sets status completed, `completed_at` (DB clock), typed result ref, clears the lease; `fail()` sets failed + clears lease; `renew()` extends the lease from the DB clock. SQLite fallback uses `datetime('now')` for the same predicates (test-only; PostgreSQL is authoritative). Implementation detail: lease/replay horizons must be computed in SQL via Core `insert(...).values(...)`, not read back into Python — SQLite returns `datetime('now')` as a string, which the ORM DateTime type rejects on INSERT.
- **SQLite unit tests** (`backend/tests/test_idempotency_service.py`, 9 tests): **9 passed** — claim → complete → replay; hash mismatch; wrong-token completion; completion after expiry (0 rows); renew before/after expiry; worker failure before/after expiry; reclaim after expiry; attempt cap at 5; unknown operation rejected.
