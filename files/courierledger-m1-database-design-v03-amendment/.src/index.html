Technical Correction Amendment v0.3

A targeted follow-up amendment to the Database Design Specification v0.1 (36 pages), as already amended by Technical Correction Amendment v0.2. This amendment supersedes only the sections, tables, constraints and test scenarios it explicitly names. Everything else in v0.1 and v0.2 stands unchanged.

Scope guard. This document contains no application code and no executable migrations. SQL fragments and index definitions are illustrative design notation, marked ADAPT, exactly as in v0.1 Section E and v0.2. No courier rate, fee, statement format or contract semantic is invented. V2.2.1 formulas, integer BIGINT poisha, per-component half-up rounding, NULL versus verified zero, and the explicit Dc confirmation-plus-evidence rule are preserved without modification. CL-01 to CL-12 are preserved unless a concrete contradiction is demonstrated - and the one wording contradiction found is corrected in CL-17, with the underlying CL-01 rule unchanged.

What this amendment does

  • Resolves four follow-up findings, CL-13 to CL-16, each in the established six-part form: original problem, exact change, affected section and table, constraint or transaction-level enforcement, updated test scenario, and a resolved / still-open verdict.
  • Provides one implementation clarification, CL-17, on how PostgreSQL actually enforces cross-table consistency - correcting a phrase in v0.2 CL-01 without changing the CL-01 rule itself.
  • Adds two tables, and only two, both under CL-16, where the existing schema is shown to be unable to hold the required history. The design total moves from 29 tables to 31.
  • Ends with consolidated test changes, a traceability delta, a change log and the remaining blockers.

Reading rule. Where this amendment and v0.1 or v0.2 disagree, this amendment wins for the named item only. Where it is silent, v0.1 as amended by v0.2 applies.

Gating - unchanged. M1 production implementation remains gated behind the Day 7 and Day 14 market-validation gates, merchant-confirmed courier evidence, a Docker + PostgreSQL verification environment, and explicit production-readiness approval. This amendment authorises none of those steps, and no test in it is claimed to have passed.

Both are examined in the findings below and rejected, with reasons, in favour of mechanisms that keep the existing invariants intact. Rejecting an option is part of the correction: a future implementer should not have to re-derive why the obvious-looking route was not taken.

CL-13 - Match decision branching and concurrency: one linear chain per candidate

1. Original problem

v0.2 CL-03 made match decisions immutable by moving them into the append-only table shipment_match_decisions, with a nullable self-reference, supersedes_decision_id, set when a later decision replaces an earlier one. That solved the mutability problem but left the shape of the decision history unspecified in four ways.

  • Branching is representable. Nothing prevents two decisions from both naming the same decision as the one they supersede. The history then forks, each branch with its own latest decision, and the phrase in CL-03 - "the latest decision row for that candidate that has not itself been superseded" - identifies two rows, which may disagree: one ending in confirmed, the other in rejected.
  • Cross-candidate supersession is representable. The v0.2 self-reference is a plain foreign key to the decision's own table and does not require the superseded decision to belong to the same candidate: a decision about candidate A can claim to supersede one about candidate B, making per-candidate derivation meaningless.
  • Concurrent first decisions have no serialisation rule. CL-03 noted that concurrent first decisions must both be recordable so a conflict is visible, and relied on a deferred constraint trigger aimed at a different problem - a second current confirmation across candidates of the same statement line. Two reviewers deciding the same candidate at the same moment, one confirming and one rejecting, were given no rule for what happens, in what order, and what the candidate's current decision then is.
  • Cycles are not addressed. CL-03 does not state whether a supersession cycle (A supersedes B, B supersedes A) is possible or how it is prevented. A derivation that walks a chain containing a cycle does not terminate, so the question is not academic.

The result is that the most audit-sensitive derivation in the matching design - "what is this candidate's current decision?" - was deterministic only in the easy cases.

2. Exact proposed change - definitions

Supersedes the decision-history paragraphs of v0.2 CL-03 and CL-07 where they describe derivation and concurrency. The tables and their append-only class are otherwise unchanged. Four terms are defined once:

TermDefinition
RootA decision row for a candidate whose supersedes_decision_id is NULL. The first decision about that candidate.
SuccessorDecision X is the successor of decision Y when X.supersedes_decision_id = Y.id. Y is then the predecessor of X.
HeadA decision that has no successor. In a well-formed history there is exactly one head per candidate.
ChainThe sequence formed by starting at the root and following successor links to the head. A well-formed history for one candidate is exactly one chain containing every decision row for that candidate.

The linear-chain rule. For each candidate, the decision history is a single linear chain: exactly one root, at most one successor per decision, and every decision belonging to the chain. Sections 4 and 5 separate how this is prevented from breaking, how a break is detected if prevention is bypassed, and how a broken history is resolved without editing any row.

CL-13 - Match decision branching and concurrencyDesign only - M1 implementation remains gated

2. Exact proposed change (continued) - prevention, derivation, conflict

(a) Prevention in normal operation - serialised inserts. Every decision insert runs in a transaction that first takes a transaction-scoped advisory lock keyed on the candidate (design notation, ADAPT: pg_advisory_xact_lock over a hash of the candidate ID, taken after the tenant context is set and before any decision row is read). The lock is used instead of SELECT ... FOR UPDATE on the candidate row for a deliberate reason: the runtime role holds no UPDATE grant on the append-only matching tables under Section E, and row-locking a table requires that privilege. An advisory lock needs no table privilege, does not modify the candidate row, is held only to commit or rollback, and cannot leak through a pooled connection because it is transaction-scoped. Within the lock, the inserting transaction reads the candidate's current head and follows one of two paths:

  • If no decision exists, the new decision is inserted as the root, with supersedes_decision_id NULL.
  • If a head exists, the new decision must name that head as its predecessor. A transaction that intended to record a first decision but finds, after acquiring the lock, that another decision committed first does not insert a second root: it inserts its decision as the successor of the existing head. Both reviewers' decisions are therefore preserved, in commit order, in one chain - the second decision visibly replaces the first rather than silently racing it.

The partial unique index in section 4 is the backstop: if lock discipline is ever bypassed by a code defect, a second successor insert fails with a uniqueness violation and its transaction rolls back, rather than committing a fork. A rolled-back attempt of that kind is an application error to be logged and retried through the locked path - it is not a committed decision, and nothing in this design treats it as one.

(b) Deterministic derivation of the current decision. The current decision for a candidate is derived by the following steps, in order, over that candidate's decision rows. The derivation is a pure function of the stored rows: it uses no timestamps to choose a winner, because two rows can share a timestamp and wall-clock order is not evidence.

  1. If the candidate has no decision rows, it is undecided. Its match basis remains a proposal only, exactly as in v0.1 D.7.
  2. Count roots and heads, and walk the chain from each root. If there is exactly one root, exactly one head, and the single walk visits every decision row for the candidate exactly once, the history is well-formed and the current decision is the head.
  3. If there are multiple heads but every head's decision is rejected, the candidate is closed by unanimous rejection: its current decision is derived as rejected. No branch asserts a confirmation, so no branch can attach reported money to a shipment, and the disagreement among the branches has no financial consequence.
  4. In every other case of a malformed history - multiple roots with disagreeing heads, or multiple heads of which at least one is confirmed - the candidate is conflicted and has no current decision. A conflicted candidate must not be used by a reconciliation run, must not satisfy the "current derived decision is confirmed" condition in CL-03, and produces a data-quality finding on any result that would otherwise have relied on it, so the shipment is classified needs_review under the CL-01 precedence.

(c) Conflicting initial decisions - preserved and detected, never overwritten. A conflicting pair of initial decisions can reach the table only outside the locked path: for example through a pre-v0.3 data state, or a migrator-role maintenance write. This amendment does not pretend the lock makes such rows impossible in principle; it specifies what the design does with them. They are preserved exactly as inserted - the append-only grants already make any cleanup by edit or deletion impossible for the runtime role. They are detected in two places: the derivation above returns conflicted rather than picking a winner, and test T-26 requires the detection to be demonstrated on deliberately malformed data written by the migrator role - a property of the derivation, not of a stored flag that could itself be wrong.

2. Exact proposed change (continued) - resolution, and why branches are never merged

(d) Resolving a conflicted candidate. Two resolution paths exist, and neither edits history:

  • Close it. For each head that is not already a rejection, insert a successor decision of rejected, through the normal locked path, naming that head as predecessor and recording the conflict as the reason. When every head is a rejection, derivation step 3 applies: the candidate is closed, permanently, as rejected. This is always available and is the correct outcome when the disagreement itself makes the candidate untrustworthy.
  • Supersede the candidate, not the branch. If the match itself is still believed correct, a new candidate row is created for the same statement line, shipment and match basis, carrying a new nullable column prior_candidate_id - a composite self-referencing foreign key to the conflicted candidate, same tenant - recording that this candidate replaces it. Decisions about the new candidate start a fresh, well-formed chain. The conflicted candidate and its full branching history remain stored and queryable. Nothing in Section C makes (statement line, shipment, match basis) unique, so the successor candidate is representable without weakening any existing constraint; its rank orders it after the candidate it replaces.

(e) Why merging branches is rejected. The alternative - a resolution decision that supersedes two heads at once, joining the branches - was considered and rejected. A single supersedes_decision_id column cannot express a two-predecessor join; expressing it honestly would need a link table and would change the history from a chain into a directed graph, with a derivation rule to match, for the sake of an anomaly that the locked path already prevents in normal operation. Quarantining the candidate and, where needed, superseding it keeps one simple invariant - one candidate, one chain - that every reader, query and test can rely on.

(f) The statement-line level is a separate question, with a simpler answer. CL-03's deferred constraint trigger concerned a different conflict: two different candidates for the same statement line both currently confirmed. That conflict needs no quarantine mechanism, because each candidate's own chain can advance independently: superseding one candidate's confirmed head with a rejection leaves exactly one currently confirmed candidate, and the line-level invariant holds again. The trigger specified in CL-03 is retained as the commit-time backstop for that invariant, and CL-17 below classifies it correctly as a deferred constraint trigger. The derivation of "the confirmed candidate for a line" is then: the unique candidate whose derived current decision is confirmed; if two qualify, the trigger has been bypassed, the line is treated as ambiguous under v0.1 D.7, and no automatic choice is made.

(g) Cycles cannot occur. The proof is short and rests on immutability rather than on any check. A cycle would require some decision row to name, directly or through a chain, itself as a predecessor. A row's supersedes_decision_id is set only at insert, can reference only a row that already exists (the foreign key requires it), and can never afterwards be changed, because the table is append-only with no UPDATE grant or policy for the runtime role (Section E, restated by CL-03). Every link therefore points from a later-inserted row to a strictly earlier-inserted row, so following predecessor links strictly decreases insertion order and must end at a root. No cycle can be constructed, and no cycle-detection code or constraint is needed.

3. Affected section and table

Section C, table shipment_match_decisions (self-reference strengthened; no new columns) and table shipment_match_candidates (one new nullable column, prior_candidate_id); Section B ERD matching sub-diagram (self-reference on candidates); v0.2 CL-03 item 4 and the CL-07 mirror wording (derivation and concurrency paragraphs superseded); Section E append-only list (unchanged membership); Section I test T-26 (new, section 5). The audit-mirror rule of CL-07 is unchanged: every decision insert still writes its audit_logs row in the same transaction, and the decision table remains the source of truth if the two ever differ.

CL-13 - Match decision branching and concurrencyDesign only - M1 implementation remains gated

4. Constraint or transaction-level enforcement

  • At most one successor per decision (no branching). Partial unique index (ADAPT): UNIQUE (merchant_id, supersedes_decision_id) WHERE supersedes_decision_id IS NOT NULL on shipment_match_decisions. Roots are exempt by the predicate - the index governs successors, not roots - which is what allows the anomalous multi-root state of section 2(c) to be stored and detected rather than silently rejected by a constraint the audit then cannot see.
  • Supersession stays inside one candidate and one tenant. Add UNIQUE (merchant_id, candidate_id, id) to shipment_match_decisions and replace the plain self-reference with a composite foreign key: (merchant_id, candidate_id, supersedes_decision_id) references (merchant_id, candidate_id, id). A decision can now supersede only a decision about the same candidate in the same workspace, enforced by the database rather than by insert-path discipline. A CHECK keeps supersedes_decision_id different from the row's own id as a same-row guard, although the cycle proof in section 2(g) already makes self-reference unreachable in practice.
  • Serialisation. The candidate advisory lock described in section 2(a) is a mandatory part of the decision-insert transaction, stated here as a design invariant in the same terms CL-11 used for tenant context: decision inserts pass through one component that takes the lock, and no repository method inserts a decision without it. The unique index above is the database backstop if that invariant is violated.
  • Well-formedness at commit. Chain-shape rules that span rows - one root, chain visits every row - are cross-row invariants and are therefore not expressed as CHECKs (see CL-17). They are verified by a deferred constraint trigger (ADAPT) on shipment_match_decisions that, at commit, re-derives the candidate's state using section 2(b) and rejects the transaction if it would leave a newly written history malformed through the application's own path. Rows written by the migrator role outside that path are the detection case of T-26, not a state the trigger is asked to repair: triggers reject transactions; they do not rewrite history.
  • Immutability unchanged. No UPDATE or DELETE policy or grant is added for either matching table. The lock, the indexes and the trigger all operate on inserts only.

5. Updated test scenario

T-26 (new) - Match decision chain integrity and concurrency. (a) Through the locked path, confirm a candidate, then supersede with a rejection, then supersede with a confirmation: exactly one chain of three rows exists, the derived current decision is the final confirmation, and T-21's assertions still hold. (b) Two concurrent transactions decide the same undecided candidate, one confirming and one rejecting: both decisions are committed, in one chain, in commit order; the derived current decision is the second transaction's decision; no second root exists. (c) Attempt, bypassing the application path as the migrator role, to insert a second successor of an existing decision: rejected by the partial unique index. (d) Attempt to insert a decision superseding a decision belonging to a different candidate, and separately to one in a different workspace: both rejected by the composite foreign key. (e) Insert two roots for one candidate as the migrator role, one ending confirmed and one rejected: the derivation reports the candidate conflicted with no current decision, a run that would rely on it classifies the shipment needs_review with a data-quality finding, and neither row has been altered. (f) Close the conflicted candidate by rejecting every non-rejected head: the derivation now reports rejected under the unanimous-rejection rule. (g) Create a successor candidate linked by prior_candidate_id, confirm it through the locked path, and confirm the run snapshot records the new candidate's decision row ID while the conflicted candidate's history remains fully queryable.

6. Status

Resolved. The decision history is now a defined linear chain: branching is prevented by a unique index, cross-candidate links are prevented by a composite foreign key, concurrent inserts are serialised by a transaction-scoped lock chosen to respect the append-only grant model, current-decision derivation is deterministic in every state including malformed ones, cycles are shown to be structurally impossible, and conflicts are preserved, detected and resolvable without a single UPDATE or DELETE. Immutable decision history - the point of CL-03 and CL-07 - is not weakened; it is what makes the cycle proof and the conflict-preservation rule possible.

CL-14 - Idempotency recovery: abandoned claims, leases and crash windows

1. Original problem

v0.2 CL-04 established one authoritative idempotency store, idempotency_keys, with a lifecycle of in_progress, completed and failed: the key row is claimed in its own short transaction, the work transaction on success marks it completed and sets the typed result reference, and a rolled-back work transaction leaves the key to be marked failed by a compensating update so that a same-hash retry may re-execute. That design answers replay and hash-conflict questions, but it leaves the failure it most needs to survive - a process that stops mid-operation - unspecified in three ways.

  • A crashed claim is indistinguishable from a running one. If the worker crashes after claiming a key, or crashes before the compensating failed-marking runs, the row sits at in_progress indefinitely. CL-04 gives no rule for when another worker may treat the claim as abandoned. Every later retry with that key then faces a row that is neither completed (so there is no result to return) nor failed (so re-execution is not authorised). The operation is wedged - safely, but permanently.
  • Reclaiming without ownership invites the duplicate the table exists to prevent. The obvious fix - "let a retry take over a stale in-progress row" - creates the opposite defect if it is not fenced: the original worker may not be dead, only slow or partitioned. If a second worker re-executes while the first is still working, and the first then completes, two import batches or two runs can be created for one key. For run creation, CL-05's UNIQUE (merchant_id, run_hash) would still collapse identical inputs to one run; for import creation there is no equivalent content-level backstop stated. An unfenced takeover is therefore not an acceptable recovery rule.
  • The crash window between work and key completion is unexamined. CL-04's wording puts the completion update in "the work transaction", but does not state the requirement strictly enough to reason about: if the work and the completion were ever in separate transactions, a crash between them would leave a committed result that no key points to, and a retry would create a second one. Whether that window exists is a property of the transaction boundary, and the amendment must close it explicitly rather than assume it away.
CL-14 - Idempotency recoveryDesign only - M1 implementation remains gated

2. Exact proposed change - lease, token and attempt columns

Clarifies and extends v0.2 CL-04, item 2 and item 4. The table remains the sole idempotency owner; the operation list, typed result references, uniqueness and request-hash rules are unchanged. Four columns are added to idempotency_keys:

ColumnType / nullMeaning
lease_expires_atTIMESTAMPTZ, NULLEnd of the current claim's ownership window. Set at every claim and reclaim; NULL on completed and failed rows. A claim is live while this is in the future and abandoned once it has passed.
claim_tokenUUID, NULLA fresh random token generated at every claim and reclaim - the fencing token for this attempt. Only the holder of the current token may complete or fail the key. Holds no credential and no user information.
attempt_countINTEGER, NOT NULL, DEFAULT 0, CHECK >= 0Number of times the key has been claimed. Incremented atomically by the claim or reclaim that wins. Bounds recovery work: see the attempt cap in section 2(g).
claimed_by_instanceTEXT, NULLOpaque identifier of the application instance holding the claim, for operational diagnosis only. Not an actor identity, not a credential, and never used for authorisation - the token, not the label, fences the claim.

Two different clocks, never conflated. CL-04's expires_at remains the replay horizon: how long a completed result may be returned for a replayed key, after which the row may be purged by the maintenance role and the key string claimed fresh. The new lease_expires_at is the ownership horizon: how long one worker may hold an unfinished claim. The lease is measured in minutes; the replay horizon is the 24-hour design default set by CL-04. Reclaiming a lease never extends expires_at, and expires_at passing never, by itself, authorises re-execution of an operation whose status is completed - it ends the replay guarantee, which is a different statement, addressed in item (f) below.

CL-14 - Idempotency recoveryDesign only - M1 implementation remains gated

2. Exact proposed change (continued) - claim, reclaim, completion

(a) Claim. As in CL-04, the key row is inserted in its own short transaction, now with status in_progress, attempt_count = 1, a fresh claim_token and lease_expires_at set to the claim time plus the operation's lease duration. Lease durations are operational configuration, not business rules: the design default is 5 minutes for import_create and 10 minutes for run_create (ADAPT - to be set from measured operation times in the verification environment, and always comfortably longer than the operation's normal duration and far shorter than the replay horizon). A worker that is still legitimately working as its lease nears expiry may extend the lease by a conditional update that matches its own current claim_token; a worker whose token no longer matches cannot extend, complete or fail the key, under any circumstances.

(b) Reclaim of an abandoned claim. A retry that finds its key at in_progress with an expired lease attempts exactly one atomic, conditional update (design notation, ADAPT): set a fresh claim_token, a new lease_expires_at, increment attempt_count and record the reclaiming instance, where the row's key, operation and request_hash match the retry, its status is in_progress, and its lease has expired. The database executes that update against at most one row, so among any number of concurrent reclaimers exactly one wins; the losers observe the new live lease and behave as ordinary concurrent retries - they wait within a bounded period or return the operation's in-progress state to the caller, and they do not execute the work. A retry whose hash differs from the stored hash is a conflict error in every state of the row - live, abandoned, failed or completed - exactly as CL-04 requires; abandonment never launders a hash conflict into a fresh execution.

(c) Completion is in the work transaction - the crash window is closed, not managed. This amendment makes explicit what CL-04 implied: the update that marks the key completed and sets its typed result reference is the last write of the same transaction that creates the result, and that update is conditional on the row still carrying the worker's claim_token and status in_progress. If the conditional update affects zero rows - because the lease was reclaimed and the token rotated - the work transaction must roll back in full, discarding the result it created. The consequences are strict: a result and its key completion commit together or not at all, so no committed result can exist without its key pointing at it; and a displaced ("zombie") worker cannot commit duplicate work, because its completion is the one write it is no longer able to make, and that write gates its whole transaction.

(d) Failure. The CL-04 compensating update is retained and fenced in the same way: a worker that knows its work has rolled back marks the key failed, conditional on its own token, clearing the lease. A failed key may be re-claimed by a same-hash retry immediately, without waiting for any lease. If the worker crashed before it could mark failure, the lease expiry path of (b) reaches the same outcome more slowly. Both paths converge on one rule: re-execution is authorised either by a failed row or by an expired lease - never by the mere passage of an arbitrary wait, and never by a second live claim.

The four crash windows, stated individually

WindowOutcome under this design

W2. Crash during the work transactionThe work transaction rolls back, so no partial result exists. Recovery proceeds as W1: lease expiry, reclaim, one execution.
W3. Crash after work commits, before the caller receives the responseThere is no "after work commits but before the key completes" state, by rule (c): they are one commit. The retry finds a completed key and receives the original typed result reference. No re-execution.

2. Exact proposed change (continued) - replay, expiry and the attempt cap

(e) Completed replay is unchanged, and total. A retry with the same key, operation and hash against a completed row returns the typed result reference and executes nothing, at any point before expires_at - including a retry that arrives after one or more abandoned-claim episodes earlier in the key's life. The history of claims is operational detail; the completed row is the answer.

(f) What expiry does and does not end. After expires_at, CL-04 permits the maintenance role to purge the key row and the same key string to be claimed fresh - that is, the deduplication guarantee for that key string ends. Two existing safeguards bound the risk, and this amendment relies on them rather than inventing a third: for run_create, CL-05's UNIQUE (merchant_id, run_hash) deduplication is content-based and has no expiry, so a post-expiry duplicate run request still resolves to the one existing run; for import_create, the file-level hash detection in Section C (file_objects hash per merchant) is the corresponding second layer, and an import retry after key expiry must be checked against it before a new batch is created. What expiry must never do is delete or alter the created batch or run themselves - CL-04 already states this, and it is repeated here because recovery logic is exactly where such a cleanup would be attempted.

(g) Attempt cap. Recovery must not loop forever on an operation that crashes every worker that touches it. When a claim or reclaim would raise attempt_count above the operation's configured cap (design default 5, ADAPT), the row is instead moved to failed, its lease cleared, and further retries with the same key return an explicit terminal-failure response directing the caller to investigate and, if appropriate, submit under a new key. The cap is enforced inside the same conditional update, so concurrent reclaimers cannot race past it. A capped key is a visible operational event, recorded in the application log outside the tenant tables in the manner of CL-11 - a repeatedly crashing financial operation is something operators must see, not something the table should quietly absorb.

CL-14 - Idempotency recoveryDesign only - M1 implementation remains gated

3. Affected section and table

Section C, table idempotency_keys (four columns added; status list unchanged - abandoned is a derived condition, in_progress with an expired lease, not a fourth status, so no CHECK list changes and no stored flag can disagree with the clock); Section H (the shared idempotency component of CL-04 gains the claim, reclaim and completion protocol above); Section I test T-10 (assertions extended by T-27, section 5). Sections C and H of v0.1 are affected only through the CL-04 supersession chain. No other table changes: in particular, no lease or token column appears on import_batches or reconciliation_runs, preserving CL-04's single-owner rule.

4. Constraint or transaction-level enforcement

  • Uniqueness remains the arbiter of first claim. UNIQUE (merchant_id, operation, idempotency_key) is unchanged; the losing claimant of a race sees the existing row and follows the reclaim, wait or replay path - no check-then-insert in application code is relied on, as CL-04 already required.
  • Reclaim and completion are single conditional updates. Each is one UPDATE whose predicate includes the expected status, the lease condition where relevant, and - for completion and failure - the caller's claim_token. PostgreSQL's row locking makes each such update atomic against concurrent updaters of the same row: exactly one reclaim wins, and a completion by a displaced token matches zero rows. These are transaction-level mechanisms, stated as such; no CHECK constraint is claimed to perform them (see CL-17).
  • State-to-column consistency is row-local and is a CHECK. completed requires completed_at NOT NULL, the operation's typed result reference NOT NULL (per CL-04's existing CHECK) and lease_expires_at NULL; in_progress requires lease_expires_at NOT NULL and all result references NULL; failed requires lease_expires_at NULL and all result references NULL. Each condition inspects only the row itself, which is precisely what a CHECK may do.
  • RLS and roles unchanged. CL-15 - Workspace anonymisation and tenant integrity: the tombstone merchant

1. Original problem

v0.2 CL-12 specified a two-stage model - closure, then erasure - and said financial history would be "retained in anonymised-tenant form - merchant identity link severed, amounts and rule snapshots intact". That sentence contains an unspecified mechanism, and each obvious way of implementing it breaks a different part of the design:

  • Deleting the merchant row is rejected by the database itself: every financial table references merchants through foreign keys that CL-12 confirmed as ON DELETE RESTRICT. The row cannot go while history exists - which is the point of the restriction.
  • "Severing the identity link" by rewriting merchant_id on retained rows would require UPDATEs across runs, results, findings, fee lines, statement lines and settlement records - tables whose defining property is that the runtime role cannot update them at all, and whose snapshots are supposed to be the historical fact. It would also falsify those rows: a run would claim to belong to a workspace it never belonged to.
  • Anonymising only the merchant's name leaves the people unanswered. A workspace's members are users rows, and a user is not owned by a workspace: the same person may hold memberships in several workspaces. CL-12 said "user personal fields are anonymised" in the context of one workspace's erasure, without stating what happens when that user is an active member of another workspace that is not closing. Taken literally, closing one workspace could erase the sign-in identity a person still uses daily in another.
  • RLS has no stated post-anonymisation behaviour. Retained rows carry a merchant_id that no living session can legitimately assert once memberships have ended, and CL-12 did not state what that means for reachability or lawful export.

2. Exact proposed change - the tombstone merchant record

Clarifies v0.2 CL-12 Stage 2 and Section G. The central decision is this: the anonymised retention workspace is the same merchant row, anonymised in place. Anonymisation is an operation on identity-bearing fields of mutable identity-class rows. It is never an operation on merchant_id, and it never touches a financial row. Stage 2 for a closed workspace performs, in one migrator-role maintenance transaction:

  • On merchants: name is replaced with a non-identifying label of the form "Anonymised workspace" plus an opaque token that encodes no personal data; trading_name is set NULL; the new column anonymised_at (TIMESTAMPTZ, NULL) is set. The row's id - the value every merchant_id in the database references - is unchanged, and status remains closed. Anonymising the business name is mandatory, not optional: for a sole proprietor the trading name may itself be personal data, and a design that scrubs the person but keeps the shop name has not anonymised anything.
  • On merchant_courier_accounts of that workspace: merchant_account_ref is set NULL and display_label replaced or nulled where it contains identifying text. Courier account references are the merchant's identifiers with third parties and have no place in retained history; the internal courier identity survives through courier_id, which is global reference data and identifies no merchant.
  • On file_objects and stored bytes: as CL-12 already specified - bytes are purged, purged_at is set, and the metadata row with its hash remains so historical references still resolve.
  • On financial and append-only tables: nothing. No UPDATE, no DELETE, no merchant_id change. Runs, results, findings, fee lines, statement lines, import rows, allocations and - under CL-16 below - variance calculations remain byte-identical, with amounts, snapshots and rule provenance intact.

The result is a tombstone merchant: a tenant root that still exists for every foreign key that needs it, still scopes its retained history under its own original merchant_id, and no longer identifies anyone.

CL-15 - Workspace anonymisation and tenant integrityDesign only - M1 implementation remains gated

2. Exact proposed change (continued) - options rejected, and the shared user rule

Why not a shared anonymised retention workspace. The alternative considered - one special "retention" merchant to which every closed workspace's financial rows are transferred - is rejected for four concrete reasons. First, the transfer is the forbidden rewrite of merchant_id on append-only rows described above. Second, it merges tenants: histories of unrelated businesses would come to share one merchant_id, ending the one-workspace-one-tenant correspondence the whole of Section E rests on. Third, it corrupts scoped uniqueness: run deduplication is UNIQUE (merchant_id, run_hash) (CL-05), and two transferred workspaces could present the same hash under the retention tenant and collide. Fourth, it makes isolation unprovable for the retained data, because an RLS context asserted for the retention tenant would expose every transferred workspace at once. The tombstone keeps each workspace's history under its own key, which is what "tenant isolation for retained records" has to mean.

The shared user rule. User anonymisation is governed by the user's position across all workspaces, never by one workspace's closure alone. The rule is deterministic:

  1. When a workspace is anonymised, its merchant_memberships rows - already ended at closure under CL-12 Stage 1 - are left as historical records of role and period. A membership row carries no personal fields beyond its foreign keys, so it needs no scrubbing; the identity question is entirely about the users row it points to.
  2. A users row is anonymised - email replaced with a non-routable anonymised placeholder unique to that row, display_name set NULL, credential material removed, status set to closed - only if the user has no membership in active or invited state in any workspace, and no live session. The eligibility test is evaluated globally at the moment Stage 2 runs, not inferred from the closing workspace.
  3. If the user has any active membership elsewhere, their users row is not touched in any way by this workspace's anonymisation. They keep signing in; the other workspace's audit attributions keep resolving; nothing about them is recorded in the closing workspace's anonymisation audit beyond the fact that a member's identity was retained because of other memberships - a fact recorded without naming the other workspace.
  4. Where a users row is anonymised, it is anonymised in place and the row remains: actor_user_id, created_by_user_id, decided_by_user_id and similar attributions across retained history continue to reference an existing row, preserving referential integrity and provenance, while the row no longer identifies a person. A UUID that resolves to an anonymised user is a pseudonymous attribution, and the design says so plainly rather than claiming the attribution has been erased.

Worked example. A person is Owner of workspace A and a member of workspace B, both active. A closes and completes Stage 1. At Stage 2, A's tombstoning proceeds in full - business identity scrubbed, courier references nulled, file bytes purged - but the eligibility test finds an active membership in B, so the users row is untouched and the person signs in to B the next day exactly as before. If B later closes and is anonymised in its turn, the test then finds no active membership anywhere, and only at that point is the users row anonymised.

2. Exact proposed change (continued) - isolation and export after anonymisation

Tenant isolation is preserved, and is in fact at its strongest. Retained rows keep their original merchant_id; RLS remains ENABLE + FORCE on every tenant table; and tenant context can only be set from an authenticated session's resolved active membership (CL-11). A tombstoned workspace has no active memberships, so no application session can legitimately assert its context: through the runtime role the retained history is unreachable, while remaining physically intact and internally consistent. Isolation between two tombstoned workspaces is the same isolation as between two live ones - distinct keys, distinct policy scope - because anonymisation changed no key.

Historical export has two windows, and they must not be confused. The merchant-facing export - the owner's complete record of their own history - belongs to Stage 1: the workspace is closed but not yet anonymised, still readable by its former Owner for export, as CL-12 specified. That is the only window in which an identified export exists, and the length of the grace window before Stage 2 remains the open policy question in OD-16. After anonymisation, the only exports the design permits are anonymised ones, produced under the migrator-role maintenance procedure rather than the application: amounts, dates, statuses, findings and rule snapshots keyed by the tombstone's merchant_id, containing no merchant or user identity. Such an export must exclude the raw source payloads discussed immediately below.

The one conflict this amendment does not resolve: personal data inside append-only raw records. Anonymising identity rows does not reach personal data that may exist inside retained source data. import_rows.raw_values preserves each uploaded row verbatim, by design, and courier statement files may contain recipient names, phone numbers or addresses as supplied in the source file; statement lines and order references can carry merchant-supplied identifiers with similar content. orders are mutable-class rows whose identifying fields can be scrubbed in Stage 2. But import_rows and statement_lines are append-only precisely so that raw and normalised values can never be rewritten (v0.1 D.3). Scrubbing them would break the raw-preservation invariant; deleting them would break referential integrity for the runs built on them; retaining them unchanged means retained history can still contain third-party personal data after the merchant's own identity is gone. This amendment does not pick a winner among anonymisation, immutability and retention. CL-16 - Immutable bank variance history: a calculation record, not a column

1. Original problem

In v0.1, bank variance lives in exactly one place: settlement_batches.bank_variance_poisha, a single nullable BIGINT column on a table whose status and totals are otherwise mutable. v0.2 CL-10 then defined what a reversal does to a computed variance - the batch "no longer reports a current bank variance (reported as NULL) while the historical computation remains in the audit record", and a re-completion "computes a fresh variance". Taken together, the two documents require a history that the schema cannot hold:

  • One column cannot store a sequence. The first variance is overwritten by the fresh variance after re-allocation, or cleared towards NULL after a reversal. Either way the earlier computed value - a financial figure the merchant may already have seen and acted on - is gone from structured storage at exactly the moment a dispute would ask for it.
  • The audit record is not a substitute. CL-10's fallback is audit_logs.detail, a JSONB payload. It has no typed amount column, no foreign key to the receipts or allocations the calculation used, no uniqueness or sequence, and no constraint that a variance-shaped entry even exists for a given computation. Reconstructing "what variance was shown on this date, from which receipts and allocations" becomes a search through unstructured log text - the outcome this finding was raised to prevent.
  • The inputs are not snapshotted anywhere. A variance is a function of three things that can all change afterwards: the expected batch payout, the set of receipts and their completeness, and the net allocation total (which reversals change, by design). Even if each successive variance value were kept, a value without its inputs cannot be verified, and an unverifiable historical financial figure is little better than none.

The task for this amendment permitted a new table only if the existing schema cannot safely support the requirement. That test is met, and section 2 says why in one sentence: the only existing stores are a single mutable column, which cannot hold a sequence, and an unstructured audit payload, which cannot hold a verifiable calculation. Two tables are therefore added - one for the calculation, one for its typed input references - and no third: amounts, inputs and supersession can all be expressed with exactly those two.

The receipt set listed is every receipt linked to the batch at computation time, because the completeness precondition is a statement about all of them. The calculation and its complete input set are inserted in the transaction that establishes its preconditions; a partial input set is not a state this design permits to commit (see section 4).

Preconditions for a calculation row to exist at all - restated from v0.1 D.10 and v0.2 CL-10 as insert conditions: the expected payout is NOT NULL; every linked receipt is explicitly marked complete; and the batch is fully allocated on net totals. Current variance is derived, never stored. The value presented for a batch - still named bank_variance_poisha at the read surface - is: the bank_variance_poisha of the batch's highest-calculation_seq calculation, if and only if that calculation's preconditions still hold against current data: the batch's expected payout and current net allocated total still equal its snapshots, and every currently linked receipt is complete. In every other case the current variance is NULL. This is CL-10's rule, now resting on a structured comparison instead of a presentation convention.

Supersession after reversal. A reversal changes no calculation row: it makes the latest calculation fail the still-holds comparison, so current variance becomes NULL, while the history remains queryable in sequence. Re-allocation to full allocation triggers a new calculation row with the next calculation_seq, snapshotting the new net total and the then-current allocation set, including the reversal row. Supersession is derived from sequence order: there is deliberately no is_current flag, because a flag on an earlier row would have to be updated when a later calculation is inserted, and these rows are never updated The CL-10 audit row is still written for each computation and reversal, as a mirror: where CL-10 said history "remains in the audit record", this amendment corrects the emphasis - history is in the calculation table, and the audit record mirrors it, as CL-07 established for match decisions.

CL-17 - Clarification: cross-table consistency is not a CHECK constraint

1. Original problem

v0.2 CL-01, item 4, specified the enforcement of the corrected status rule in these words: "A consistency CHECK (or deferred constraint trigger, ADAPT at implementation) rejects the impossible combination overall_status = 'matched' together with any stored finding on the same result whose amount is non-zero outside the run tolerance." The parenthetical treats two different mechanisms as interchangeable options for one rule. They are not interchangeable, and for this rule only one of them exists.

The rule inspects three tables: the result's overall_status sits on reconciliation_results; the findings and their amounts sit on reconciliation_findings; the tolerance they are compared against sits on reconciliation_runs. A PostgreSQL CHECK constraint is evaluated against the single row being inserted or updated in its own table. It cannot contain a subquery, cannot reference another table, and cannot reference another row - PostgreSQL rejects such definitions at creation time. There is therefore no CHECK, on any of the three tables, that can express "matched while a live finding exists". An implementer who took the CL-01 wording at face value would either discover this at migration time and improvise, or - worse - implement the row-local half (the closed status list) and believe the cross-table half was also covered. This clarification removes the ambiguity at the source, and then applies the same discipline retroactively to every invariant in v0.1 and v0.2 whose enforcement was described loosely.

2. Exact proposed change - three mechanisms, three distinct scopes

The following definitions govern how enforcement language is to be read in v0.1, v0.2 and this amendment. Where any earlier text says "CHECK (or deferred trigger)", "write-path enforcement" or "consistency check" for a rule that spans rows or tables, it is to be read as the mechanism this section assigns - this is a clarification of enforcement, not a change to any rule itself.

CL-01 enforcement, restated correctly. The closed five-value list on overall_status remains a CHECK - it is row-local. The consistency rule is enforced by a deferred constraint trigger (ADAPT), defined on both reconciliation_results and reconciliation_findings, so that it fires whether a transaction writes the result first and its findings second, or the reverse. At commit, the trigger re-derives the expected overall status for each affected result using the CL-01 five-step precedence, reading the run's tolerance through the result's run_id, and rejects the transaction if the stored overall_status differs from the derived one. Verifying the whole derivation, rather than only the single "matched over a live finding" combination named in v0.2, costs nothing extra at commit time and closes the entire class of status errors, not one instance of it. Because results and findings are append-only, the trigger constrains creation only; there is no update path to police.

A note on trigger functions and RLS. Constraint-trigger functions execute with the privileges of the function owner, which in this design is the migrator role, not the runtime role - and under FORCE RLS the owner is itself subject to policies on row operations. Two design rules follow, stated so the implementation does not rediscover them: a trigger function used for cross-table verification must scope every query it makes by the merchant_id of the rows that fired it, explicitly, rather than relying on the caller's tenant context, which is a property of the application transaction and not of the verification being performed; and the existence of an owner-privileged trigger function is never a reason to grant the runtime role anything - triggers fire on writes the role is already permitted to make, and confer no callable surface of their own.

4. Constraint or transaction-level enforcement

The enforcement is this clarification itself, plus one standing drafting rule for all future amendments and for the implementation review: any sentence that assigns an invariant to "a CHECK" must be able to name the single table and the single row the check inspects. If it cannot, the sentence is wrong and must name a deferred constraint trigger, a foreign key, a unique index, or a locked transaction protocol instead. Reviewers are asked to apply that test to this amendment as well: the CHECKs claimed in CL-14 (key state-to-column consistency), CL-15 (none claimed across tables - eligibility is a locked transaction rule, and section 4 of CL-15 says so) and CL-16 (same-row variance arithmetic; XOR reference rule) each pass it, and each of those findings assigns its cross-table parts to triggers or locks explicitly.

A performance note, so the trigger-based design is chosen with open eyes: deferred constraint triggers fire per affected row at commit, and the status trigger re-derives a result from its findings - work proportional to findings per result, at SME statement volumes that v0.1 Section F already takes as the design scale. This is not premature optimisation territory, and no caching or denormalisation is introduced to avoid it.

5. Updated test scenario

T-29 (new) - Cross-table enforcement mechanism. (a) Attempt, as a design-review assertion recorded with the test suite, to define the matched-over-live-finding rule as a CHECK referencing reconciliation_findings: the migration defining it is expected to be rejected by PostgreSQL, and the review records that rejection as the demonstration that CL-17's premise is correct. (b) In one transaction, insert a result with overall_status = matched and then a finding on it outside tolerance: the transaction fails at commit, not at either insert. (c) Reverse the write order - findings first, result second - with the same inconsistency: the transaction likewise fails at commit. (d) A result whose findings are all within tolerance, stored as matched_with_tolerance: commits. (e) A scenario-only Vtotal finding outside tolerance stored with overall open: commits; the same rows stored with overall matched or mismatch: rejected at commit - CL-01 and CL-17 verified together. (f) A row violating the closed status list (a sixth value): rejected immediately at insert by the CHECK, demonstrating the division of labour in a single scenario.

6. Status

Resolved as a clarification. No rule changes: CL-01 stands exactly as v0.2 decided it. What changes is that the specification no longer claims an enforcement mechanism PostgreSQL does not have, every previously loose enforcement phrase has an assigned real mechanism, and a drafting test exists to keep the error from returning. This is the only item in the amendment that corrects v0.2's own wording, and it is recorded in the change log as such.

Final statement. With this amendment applied, the five audited items are settled at design level: decision histories cannot branch undetectably (CL-13), abandoned idempotency claims always recover without duplicating a financial operation (CL-14), anonymisation no longer threatens tenant integrity or shared accounts (CL-15), bank variance history is structured and immutable (CL-16), and no enforcement claim in the specification exceeds what PostgreSQL can actually do (CL-17).
