Conventions

  • Money: every amount column is BIGINT integer poisha (100 poisha = 1 taka). The suffix _poisha is mandatory in column names. No FLOAT, REAL, DOUBLE PRECISION or NUMERIC money column is permitted in M1; rates and percentages are not money and use the types stated per table.
  • Identifiers: primary keys are UUID generated by the application (or gen_random_uuid() where stated). Natural identifiers such as tracking IDs are never primary keys.
  • Time: all timestamps are TIMESTAMPTZ, stored in UTC, displayed in Asia/Dhaka by the application.
  • NULL: NULL means unknown, missing, not applicable as defined per column, or not yet calculable. NULL never means zero. Verified zero is the integer 0 plus, where a source value is involved, a data-quality state of explicit_zero.
  • Tenant: the tenant is the merchant workspace. The tenant column is merchant_id on every tenant-owned table, including tables reached only through a parent.
  • Immutability classes: Append-only (no UPDATE, no DELETE for the runtime role), Versioned (changes create a new row; the old row is closed, never edited in place except for its validity end), and Mutable (ordinary updates, audited).

A. Architecture Review

A.1 Verdict on the draft

The proposed module list is a sound starting point. Its module boundaries match the domain - identity, courier configuration, orders, import, reconciliation and settlement are genuinely different lifecycles - and it already separates raw import data, reconciliation output and bank settlement, which is the separation the financial specification depends on. It should not be adopted unchanged. Five entities are missing, two entities need restructuring, and the draft as written does not by itself deliver tenant isolation, statement-line traceability or per-fee-line rounding evidence.

Summary of changes to the draft. Add statement_lines, reconciliation_fee_lines, shipment_match_candidates, file_objects and idempotency_keys. Restructure column_mappings so a mapping belongs to a statement template and each import stores an immutable snapshot of the mapping actually used. Keep import_errors, but define it as a queryable projection of row validation, not a second source of truth. Keep workspace_settings as a strict one-to-one table rather than a JSON column on merchants, because tolerance is a typed financial control. No draft entity is deleted.

A.2 What the draft gets right

  • Rule versions and rule evidence are separate tables. That is correct and essential: a version states what was calculated, evidence states why anyone is entitled to believe it.
  • Reconciliation is modelled as runs, results and findings rather than columns on shipments. That preserves run immutability and lets findings coexist without netting.
  • Settlement separates batches, receipts and allocations. That three-way split is what makes partial bank receipts representable without inventing a variance.
  • Import separates batches, rows and errors. Raw rows can therefore survive a failed or disputed reconciliation.
  • Audit and settings are first-class, not an afterthought bolted onto user records.

A.3 Missing entities, and why each is needed

statement_linesThe draft jumps from raw import_rows to reconciliation results. There is nowhere to store the normalised courier-reported values for one shipment - reported collected COD, reported fees, reported payout - with their per-field data-quality state. Without this table, reported values would have to be parsed again at reconciliation time (so a run could not snapshot its inputs) or stored on shipments (so a second statement would overwrite the first). reconciliation_fee_linesRounding is per fee line, and the specification requires expected-basis and reported-basis fees to be shown separately. A single totals row cannot prove which line rounded, which line was NULL, or why X_e, X_r and X_R differ. One row per fee component per result carries that evidence.
shipment_match_candidatesWeak matching must be auditable and must never rely on amount alone. If only the final chosen match is stored, there is no record that a match was ambiguous, which candidates competed, or why a human confirmed one. This table stores every candidate, its match basis, its rank and its confirmation state.
file_objectsAn import batch needs a verifiable link to the uploaded file: content hash, size, storage key and upload state. Keeping only a filename on the batch makes duplicate-file detection and later re-verification impossible.
idempotency_keysCSV upload and run creation will be retried by browsers, networks and users. Without stored idempotency keys, a retry creates a second batch or a second run and the duplicate looks like new evidence.

A.4 Entities restructured, and entities questioned

EntityFinding
column_mappingsRestructure. A mapping is a property of a statement template version, not a free-standing object, and an import must not change when a template is later edited. So column_mappings holds one row per template field, and import_batches.mapping_snapshot stores the exact mapping used, as immutable JSONB. Editing a template creates a new template version row (see Section C) rather than mutating mappings in place.

Row-level validation outcomes live on import_rows and statement_lines. import_errors is a normalised, queryable record of every error and warning (batch, row, field, code, message) so support and UI queries do not scan JSONB. A database rule must keep the two consistent: an error row always references the row and field it describes.

workspace_settingsKeep as a separate one-to-one table. Tolerance in poisha, default locale and statement completeness expectations are typed, validated financial controls. Burying them in a JSON column on merchants would remove CHECK constraints exactly where they matter most.
merchantsRename in prose, keep the name in SQL. In product language this is the workspace or seller business. The table name merchants is retained to match the approved baseline and because merchant_id is the tenant key everywhere.

A.5 Normalisation and relationship problems in the draft

  • Reported values do not belong on shipments. A shipment can appear on more than one statement (an original and a correction). Reported collection, fees and payout are properties of a statement line, not of the shipment. Storing them on the shipment is a repeating-group and overwrite problem.
  • Expected values do not belong on orders alone. Original order COD and expected collectible COD are different amounts under V2.1: delivered shipments carry the amount to collect, documented partial deliveries carry only the documented partial amount, confirmed returns and cancellations carry verified 0, and unknown or in-transit outcomes carry NULL. Both amounts are therefore stored, with the outcome and its evidence, on the shipment and order as specified in Section C.
  • Findings must not be columns on results. A result has a list of independent findings. Boolean columns such as has_fee_issue would invite netting and would lose amounts. Findings are rows.
  • Every tenant table needs its own merchant_id. Deriving tenancy only through a parent join (for example, a finding reaching its merchant through result, then run) makes RLS policies slow, fragile and easy to bypass with a hand-written query. Denormalising merchant_id onto every tenant row, protected by composite foreign keys, is deliberate and is not a normalisation violation: the composite keys guarantee the copies agree.
  • Template and rule versioning must be uniform. Both statement templates and rule versions are immutable once used. The same pattern - version number, validity window, content hash, superseding row - is used for both, so reviewers learn one pattern.
  • No polymorphic foreign keys. Columns such as entity_type plus entity_id cannot be enforced by the database. Where the draft implied them (audit logs, evidence, errors), Section C either uses a real foreign key, or accepts an unenforced reference only in audit_logs and says so explicitly, with a compensating rule.

A.8 Assumptions - not confirmed requirements

  • OPEN Sellers work in a single workspace each in M1, while the membership model already supports many users per workspace and one user in many workspaces. Nothing in the schema prevents either.
  • OPEN CSV is the only ingestion route in M1 for all five couriers. No courier API table is designed, because no courier API contract has been verified.
  • OPEN Uploaded files are held in object storage outside PostgreSQL, referenced by file_objects.storage_key. Storing file bytes in the database is rejected for M1 (OD-05).
  • OPEN Bank evidence in M1 is a manually confirmed receipt record, as in V2. Bank CSV import is excluded from the MVP and no bank statement table is designed.
  • OPEN Statement templates are maintained per courier and versioned; whether a merchant may override a shared template is OD-07.

A.9 Conflicts identified, not silently resolved

Conflict 1 - audit completeness versus the ban on storing bank account numbers. Audit and receipt records must be traceable, but no bank account number, in full or in a reversible form, may be stored. Resolution proposed for review: receipts carry a merchant-supplied reference label and the last four digits only if a policy decision explicitly permits even that; the default in Section C stores no digits at all, only a free-text label the merchant controls. This needs the OD-09 decision before implementation.
Conflict 2 - workspace erasure versus financial history retention. A merchant may ask for their workspace to be deleted, while reconciliation history is the product's evidence trail. Section G separates the two: personal data is erased, financial records are anonymised and retained only if a legal and policy decision says they must be. No retention period is asserted in this document.

B.5 Relationship notes a reviewer should check

  • Mandatory versus optional. A result must have exactly one run, one shipment and, where a statement line was matched, one statement line; an unmatched or missing-line result is represented with a NULL statement line plus a data-quality finding, never with a fabricated line. A settlement batch may exist with no receipts; a receipt may exist with no allocations; bank variance stays NULL in both cases.
  • Optional rule evidence. A rule version may exist in draft with no evidence, but it cannot become active for a cod_minus_delivery_fee base without a confirmation flag and evidence - enforced by CHECK constraints in Section C, not only by application code.
  • Superseded shipments keep all relationships and history. They are excluded from active reconciliation by a partial index and query rule, not by deletion or by breaking their foreign keys.
  • Uniqueness that is deliberately absent. There is no unique constraint on (merchant_id, courier, tracking_id). Duplicate tracking IDs occur in real statements and must be preserved and flagged. Uniqueness is enforced instead on the active COD-bearing shipment per order, on idempotency keys, on file hashes per merchant, and on version numbers within their parent.

D. Financial Data Integrity

D.1 Monetary storage and rounding

All money is BIGINT integer poisha. The database stores only integers; no financial calculation in SQL, in the ORM or in the engine may pass through a floating-point type. Percentages and rates are stored as integer basis points (cod_fee_rate_bps, vat_rate_bps), so a fee calculation is integer multiplication followed by a single defined rounding step.

Rounding is half-up, per fee line, exactly as approved: each fee line is rounded once, on its own, and the rounded line values are then summed into X_e, X_R and X_r. Totals are never rounded again, and a total is never produced by rounding an unrounded sum. reconciliation_fee_lines exists so this can be proved line by line for any result.

D.2 The approved formulas, unchanged

E  = expected collectible COD (from confirmed shipment outcome, Section C shipments)
R  = courier-reported collected COD          P_r = courier-reported payout
X_e = expected-basis deductions              X_r = deductions actually reported
X_R = deductions recalculated on the reported basis under confirmed rules

C       = R - E
delta   = X_R - X_e
V_R     = X_r - X_R
S       = P_r - (R - X_r)
V_cond  = P_r - P_cond
V_total = P_r - P_e

Identities that must hold whenever every term is present:
V_total = C - delta - V_R + S
V_cond  = S - V_R

For a cod_minus_delivery_fee base:
F_R = round_half_up( max(R - D_c, 0) x rate )
where D_c is the merchant-confirmed contractual delivery fee only.

Expected, courier-reported and bank-confirmed amounts are three different kinds of fact and are stored in three different places: expected values on orders, shipments and results; reported values on statement lines and results; bank-confirmed values on bank receipts and allocations. No column, view or report may substitute one for another, and no view may present a combined figure that hides which kind it is.

D.4 The contractual delivery fee: D_c, D_e and D_r stay separate

Three different delivery fees exist and are stored in three different places. D_e, the expected delivery fee, comes from the expected-basis fee line. D_r, the courier-reported delivery fee, is statement_lines.reported_delivery_fee_poisha. D_c, the contractual delivery fee, is courier_rule_versions.contractual_delivery_fee_poisha and is the only value that may be used as the subtractor in a cod_minus_delivery_fee base.

P0 patch rule, carried into M1 unchanged. D_c counts as contractual only when dc_confirmed is explicitly true AND dc_evidence_ref is non-empty. A D_c value on its own, a missing flag, a false flag, or a missing evidence reference each produce DQ_MISSING_CONTRACT, set the affected fees and payouts (F_e, F_R, P_e, P_cond) to NULL and mark the result needs_review. There is no fallback to D_e or D_r, in the engine, in SQL or in a report.

Worked synthetic illustration (fictional numbers, no real courier rate): expected delivery fee D_e = 6,000 poisha, reported delivery fee D_r = 6,500 poisha, confirmed contractual fee D_c = 6,000 poisha with evidence, reported collection R = 100,000 poisha, COD fee rate 1 percent on a cod_minus_delivery_fee base. Then F_R = round(max(100,000 - 6,000, 0) x 1 percent) = 940 poisha. Using D_r instead would give 935 poisha and would be wrong by construction, not by arithmetic - which is why the three values may never be substituted for one another. If D_c were unconfirmed, F_R would be NULL, not 935 or 940.

For a reported_collected COD fee base, the contractual fee is the reported-basis fee and the contractual payout comparison is against P_cond. V_total compares the reported payout with a hypothetical expected-collection scenario (P_e); it is information, not a contractual judgement.

D.7 Matching precedence

  1. Strong match: same workspace, same courier account, and a unique normalised tracking ID match between statement line and shipment. This is the only automatic match.
  2. Duplicate or repeated tracking: if the normalised tracking ID is not unique on either side, the line is ambiguous. It stays open for human confirmation; no automatic choice is made.
  3. Weak fallback: blank tracking ID, an exact merchant order ID matching exactly one shipment, the same courier, and a statement date within 7 days after the shipment date where both dates exist, with no other candidate. A weak match is a proposal in shipment_match_candidates and takes effect only on human confirmation.
  4. Never: no match is made on amount alone, in any code path. There is no amount value in the match_basis CHECK list, so the database itself rejects such a record.

Duplicate, unmatched and settlement-level lines are preserved as rows. They are never summed, merged or spread pro-rata across shipments.

D.8 Snapshots, rule versioning and evidence provenance

  • Run snapshot. A run copies the rule definition, rule version number and content hash, the mapping snapshot, the template version, the tolerance, the engine version, and the identifiers and hashes of every input line and shipment. A result can therefore be explained years later without reference to any live, editable row.
  • Result snapshot. Results copy E, R and P_r rather than pointing back at mutable shipment or statement values for their amounts. The foreign keys remain for navigation; the amounts on the result are the historical fact.
  • Rule versioning. Rule versions are immutable once active. A correction creates a new version, supersedes the old one, and affects only future runs. No run is ever recalculated in place; a recalculation is a new run.
  • Evidence provenance. Every active contractual value traces to a courier_rule_evidence row naming its type, reference, confirming user and time. Values with no evidence stay NULL. Public pricing pages are not evidence.
  • VAT and included tax. An included-tax amount is a breakdown of a fee that has already been counted once; it is never subtracted again. The breakdown is calculated only when the rule states an included-tax formula (rate_on_net or rate_on_gross) and the rate. If the mode is unknown, an exact payout cannot be claimed; if the mode is known to be included but only the rate is unknown, the gross fee still counts once and only the breakdown is NULL.

D.9 Reconciliation immutability and historical referential integrity

Immutability in M1 is enforced at three levels, because the P0 prototype's application-level insert-only store is not sufficient for production. First, privileges: the runtime role has no UPDATE or DELETE grant on runs, results, findings, fee lines, statement lines, import rows or evidence. Second, RLS: no UPDATE or DELETE policy is defined for those tables, so even a granted statement would return no rows. Third, triggers or rules are not required if the first two levels are applied, and adding them is a defence-in-depth option for the implementation review, not a substitute for correct grants.

Historical integrity also constrains deletes elsewhere: foreign keys from financial history use ON DELETE RESTRICT. A shipment, order, rule version, template or file object that is referenced by a run cannot be deleted. Workspace closure therefore anonymises and archives rather than cascading deletes through financial tables (Section G).

D.10 Settlement and partial receipts

A settlement batch states what is expected from courier-reported figures. Bank receipts state what the merchant confirms actually arrived. Allocations connect the two, explicitly, by a human or by a deterministic rule the merchant can inspect - never by an amount match alone, and never pro-rata.

  • Multiple partial receipts against one batch are normal. Each is recorded with its own amount and date.
  • bank_variance_poisha stays NULL while any linked receipt is not explicitly marked complete, or while the batch is not fully allocated. A partial receipt produces the status partial_receipt, not a variance and not a discrepancy.
  • Only when every linked receipt is complete and the batch is fully allocated may the variance be calculated, as allocated bank-confirmed total minus expected batch payout, and stored. Before that moment any number shown would be an invention.
  • Returned shipments follow the same separation: an expected return fee, or an amount showing as owed at batch level, is not evidence that money moved. Only a receipt is evidence of settlement.

E. PostgreSQL RLS Design

Tenant isolation rests on five things working together. Any one of them on its own - including the presence of merchant_id - is not isolation.

  1. Every tenant-owned table carries merchant_id and has RLS enabled and forced.
  2. The application connects as a non-superuser role that does not own the tables and has no BYPASSRLS attribute.
  3. Every transaction sets the tenant context as a transaction-local setting before it touches data.
  4. Policies fail closed: with no context set, they match no rows for reads and reject writes.
  5. Composite tenant foreign keys make cross-tenant relationships impossible even for a privileged writer.
All SQL in this section is illustrative and marked ADAPT. Role names, schema names and grant lists must be adapted to the chosen managed PostgreSQL service, reviewed by a second engineer, and exercised by the Section I tests before any production use. Do not run it unchanged against a live database.

E.2 Tenant context: transaction-local, set on every transaction

-- ADAPT: called by the application at the start of EVERY transaction,
-- after authentication has resolved the active workspace.
-- The third argument (true) makes the setting transaction-local:
-- it disappears at COMMIT or ROLLBACK and cannot leak to the next
-- transaction that reuses the pooled connection.
SELECT set_config('app.merchant_id', :merchant_id, true);
SELECT set_config('app.user_id',     :user_id,     true);

-- Helper used inside policies. Returns NULL when unset or malformed,
-- which makes every policy below fail closed.
CREATE OR REPLACE FUNCTION app_current_merchant_id() RETURNS uuid
LANGUAGE sql STABLE AS $$
  SELECT NULLIF(current_setting('app.merchant_id', true), '')::uuid
$$;

Two rules are non-negotiable. First, SET without LOCAL, and session-level set_config(..., false), are forbidden in application code: with connection pooling they attach the tenant to the connection, and the next request on that connection inherits it. Second, the context is set inside the transaction that does the work, never in a separate earlier transaction on the same connection.

E.3 Enablement and policies

-- ADAPT: repeat for every tenant-owned table.
ALTER TABLE shipments ENABLE ROW LEVEL SECURITY;
ALTER TABLE shipments FORCE ROW LEVEL SECURITY;
-- FORCE matters: without it, the table owner is exempt from policies.

CREATE POLICY shipments_select ON shipments
  FOR SELECT TO courierledger_app
  USING (merchant_id = app_current_merchant_id());

CREATE POLICY shipments_insert ON shipments
  FOR INSERT TO courierledger_app
  WITH CHECK (merchant_id = app_current_merchant_id());

CREATE POLICY shipments_update ON shipments
  FOR UPDATE TO courierledger_app
  USING      (merchant_id = app_current_merchant_id())
  WITH CHECK (merchant_id = app_current_merchant_id());
-- The WITH CHECK on UPDATE prevents moving a row to another tenant.

CREATE POLICY shipments_delete ON shipments
  FOR DELETE TO courierledger_app
  USING (merchant_id = app_current_merchant_id());

For append-only tables (runs, results, findings, fee lines, statement lines, import rows, import errors, evidence, audit logs) there is deliberately no UPDATE policy and no DELETE policy, and no corresponding grant. The absence is the control: an UPDATE from the runtime role affects zero rows and a DELETE is denied, which the tests assert explicitly. For merchants itself, the SELECT policy is membership-based - a user may see a workspace only where an active membership row links them - and workspace creation runs through a controlled function rather than a general INSERT policy. For users and couriers, which are not merchant-scoped, access is controlled by grants and application authorisation, and that difference is stated rather than disguised as an RLS policy.

E.4 Grants: least privilege per table class

-- ADAPT: generate per table from the classification in Section C.
-- Mutable tenant tables:
GRANT SELECT, INSERT, UPDATE, DELETE ON shipments
  TO courierledger_app;
-- Append-only financial history:
GRANT SELECT, INSERT ON reconciliation_runs,
  reconciliation_results, reconciliation_fee_lines,
  reconciliation_findings, statement_lines
  TO courierledger_app;
-- Reference data:

The single permitted exception is the run status transition (running to completed or failed, plus completed_at). Implement it either as a column-level UPDATE grant on those two columns with an UPDATE policy restricted to them in effect, or as a SECURITY DEFINER function owned by the migrator that validates the run's merchant against the caller's context. The function route is recommended: it keeps the table grant clean and gives one auditable place for the transition. Either way, no other column of a run may ever be updated.

F.2 What is deliberately not indexed or built

  • No full-text index, no trigram index and no JSONB GIN index in M1. raw_values and snapshot columns are read by key, not searched. If support later needs raw-row search, that is a measured addition, not a guess now.
  • No partitioning in M1. import_rows and audit_logs are the first candidates if row counts ever justify it, and both are already keyed by merchant and time in a way that would allow it later.

F.3 Scaling notes

SME statement volumes are modest: the design target is correctness under concurrent imports by one merchant and steady use by many small merchants, not bulk throughput. The realistic growth pressures are import_rows volume, audit volume and the number of tenants sharing one database. The responses, in order, are: retention and purging of raw file bytes (Section G), archival of audit logs, and only then partitioning or a per-tenant schema discussion - which would be a new architecture decision, not an optimisation. Any query that cannot use a tenant-first index should be treated as a bug.

H. SQLAlchemy 2.x and Alembic Design

This section describes organisation and patterns only. It is not an application implementation.

H.1 Model organisation

  • One models module per domain module - identity, courier configuration, orders, import, reconciliation, settlement, audit - mirroring the modular monolith. A shared base module holds the declarative base, the tenant mixin and the timestamp mixin.
  • The tenant mixin contributes merchant_id, the composite UniqueConstraint(merchant_id, id) and the standard tenant indexes, so a model cannot quietly omit them.
  • Money columns are declared as BigInteger with the _poisha suffix enforced by a naming convention and a lint check over the metadata. Rate columns are Integer basis points. No model may declare a float type for a financial field.
  • Enumerations are stored as TEXT with database CHECK constraints, not as PostgreSQL ENUM types: CHECK lists can be extended in an ordinary migration, while altering an ENUM type is more restrictive and harder to roll back. The Python side mirrors the same closed lists.
  • JSONB is used only where the content is genuinely a snapshot or a raw record: raw_values, mapping_snapshot, rule_snapshot, input_snapshot, rule_definition and audit detail. Anything queried, joined, constrained or summed gets a real column.

H.2 Relationship strategy

  • Relationships are defined for navigation within a module. Cross-module access goes through the owning module's repository or service, not through a lazy relationship that can wander across the whole graph.
  • No lazy loading in request paths. Queries state their joins and eager-loading explicitly, so the SQL a reviewer sees is the SQL that runs - which matters when the reviewer is checking that a query is tenant-scoped.
  • Cascades are set to RESTRICT semantics at the database level for anything referenced by financial history. ORM-level cascade deletes are disabled for those models; deletion is a workflow, not a side effect of removing an object.
  • Composite foreign keys are declared explicitly in the models so that the ORM and Alembic generate the same constraints the ERD shows. A model whose foreign key is single-column where Section C requires a composite is a review failure.

H.3 Tenant-aware repository pattern

  • There is no repository method that runs without a tenant. Every repository is constructed with a session that already carries a resolved tenant context object, and its methods take no optional merchant parameter - an optional parameter is exactly how an unscoped query gets written by accident.
  • One unit-of-work boundary per request: open the transaction, set the tenant context with set_config(..., true), do the work, commit. The context is never set outside a transaction and never reused across transactions.
  • The ORM session must not use a connection that another request's transaction has touched without the context being reset by the transaction boundary itself. Session-level state, including any cached identity map, is per-request.
  • Queries still filter by merchant_id explicitly even though RLS would filter anyway. Defence in depth is deliberate: the explicit predicate makes intent visible in review and keeps query plans on the tenant-first indexes, while RLS remains the guarantee if a predicate is ever missed.
  • Admin or cross-tenant operations do not exist in the repository layer. If a genuine operational need appears, it is a separate reviewed tool with its own role and audit trail, not a boolean flag on a repository.

H.4 Alembic migration structure

  • Migrations connect as the migrator role, never as the runtime role. The runtime role is granted privileges by a dedicated, reviewed migration (or provisioning step), not by application startup code.
  • One migration concern per revision: schema, then constraints, then indexes (built concurrently where the table may already hold data), then RLS enablement and policies, then grants. Separating RLS into its own revision makes the most safety-critical change reviewable on its own.
  • Every migration that creates a tenant-owned table must, in the same revision, add its merchant_id, its composite unique constraint, its indexes and its RLS policies. A table that exists for one revision without policies is an open table.
  • Autogenerate is a drafting aid only. Every autogenerated revision is reviewed line by line for CHECK constraints, partial indexes, composite keys and policy statements, none of which autogenerate reliably produces.
  • Downgrades are written for structural migrations. Data and evidence migrations state plainly when they are irreversible rather than pretending a downgrade exists.
  • A CI check inspects the final metadata and the live test database: every tenant table has RLS enabled and forced, the runtime role is neither owner nor superuser and has no BYPASSRLS, and no money column has a floating type or a zero default. That check is part of the Section I suite.

H.5 Database constraints complement application validation

The division of labour is deliberate. The database guarantees the invariants that must hold no matter who writes the row: types, nullability, state-to-value consistency, tenant consistency of relationships, uniqueness, one active COD-bearing shipment per order, one confirmed match per line, and the identities between a result's stored variances when all terms are present. The application handles everything that needs context the database does not have: whether evidence is genuinely merchant confirmation, whether a statement template matches a file, how findings are explained in English and Bangla, and how a user is guided to fix a problem. Where a rule can be expressed in both places, it is expressed in both, and a disagreement between them is a bug to fix, not a choice to make at runtime.

Appendix 3 - Review checklist

  • Every table in the ERD appears in Section C with the same name, keys and relationships, and every Section C table appears in the ERD.
  • No money column uses a floating type, has a zero default, or lacks the _poisha suffix.
  • Every tenant-owned table has merchant_id, a composite unique (merchant_id, id), tenant-first indexes, RLS enabled and forced, and policies for the operations its class permits.
  • Every append-only table has no UPDATE or DELETE grant and no UPDATE or DELETE policy for the runtime role, except the single documented run-status transition.
  • D_c, dc_confirmed and dc_evidence_ref behave exactly as the P0 patch requires, and no code path falls back to D_e or D_r.
  • Bank variance cannot be written before receipt completion and full allocation.
  • No column, in any table, stores a bank account number, a raw credential or a raw session token.
  • All Section J decisions marked as blocking are recorded before the affected implementation begins.
